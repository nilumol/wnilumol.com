Overview

Strong project pages help a reader understand the problem before introducing the solution. Technical terms such as validated workflow, source provenance, and human review are visually distinct without interrupting the sentence.

The central idea

AI becomes useful in regulated work when the surrounding system makes its evidence, limits, and accountability visible.

How the workflow fits together

This diagram makes the execution hierarchy, individual steps, and retry path visible in one compact view.

Durable evaluation workflow
User prompt │ ▼ POST /api/evaluate → start(evaluateCode, [prompt]) │ ▼ evaluateCode() ← "use workflow" │ ├── generateCode() ← "use step" + AI Gateway ├── generateTests() ← "use step" + AI Gateway ├── executeInSandbox() ← "use step" + Sandbox ├── Tests pass? │ ├── Yes → return results │ └── No → loop back with error context (max 3 attempts) │ ▼ Results returned

The branching structure communicates orchestration more clearly than a row of equal cards.

Three design decisions

  1. Start with controlled sources

    Constrain retrieval to information the user is authorized to access.

  2. Expose the evidence

    Connect material claims to their source and effective version.

  3. Keep people accountable

    Use the system to support judgment, not conceal or replace it.

Implementation pattern

Inline labels like source_id, effective_version, and review_required make technical concepts distinct without turning the section into a terminal or code editor.

What the page should make clear

  • Who is experiencing the problem
  • Where friction occurs in the current workflow
  • What the proposed system changes
  • How value and risk would be measured

Takeaway

This reference combines editorial typography, generous spacing, restrained borders, technical callouts, and structured diagrams. The intent is to borrow useful design principles while preserving a distinct identity for Winston's site.
